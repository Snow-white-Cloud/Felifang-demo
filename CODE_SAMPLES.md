## 1. Хэндлер: Login

**Файл:** `samples/handlers/login.go`, [тык](/samples/internal/handlers/login.go)

**Что показывает:**
- Обработка POST-запроса с JSON
- Валидация через `go-playground/validator`
- Аутентификация пользователя
- Установка HttpOnly cookie для refresh-токена (защита от XSS)
- Обработка ошибок (401, 403, 500)

**Ключевые моменты:**
- `defer r.Body.Close()` — закрытие тела запроса
- `validationErrorResponse` — единый формат ошибок валидации
- `http.SetCookie` с `HttpOnly: true` и `SameSite: Strict`
- Разные HTTP-статусы для разных ошибок (неверный пароль, неподтверждённый email)

## 3. Хэндлер: JWKS

**Файл:** `samples/handlers/jwks.go`, [тык](/samples/internal/handlers/jwks.go)

## 4. Middleware: JWT-авторизация

**Файл:** `samples/middleware/auth.go`, [тык](/samples/internal/middleware/auth.go)

**Что показывает:**
- Проверка Bearer-токена из заголовка Authorization

- Кэширование результатов валидации для ускорения

## 6. Сервис: ProfileService

**Файл:** `samples/service/profile.go`, [тык](/samples/internal/service/profile.go)

**Что показывает:**
- Чистая архитектура (сервис зависит от интерфейсов)
- Внедрение зависимостей через конструктор

## 8 Сервис: интерфейсы (слой зависимостей)

**Файл:** `samples/service/storage.go`, [тык](/samples/internal/service/storage.go)

**Что показывает:**
- Определение интерфейсов для работы с БД
- Чистая архитектура (сервис зависит от интерфейсов, а не от реализаций)
- Тестируемость (интерфейсы легко подменить моками)
- Чёткое разделение ответственности (DBSystem vs UserRepository)

**Ключевые моменты:**
- `DBSystem` — управление подключением и транзакциями
- `UserRepository` — все операции с пользователями
- Все методы принимают `context.Context` и `*sql.Tx` (для транзакций)
- Возвращаемые типы (uuid.UUID, bool, error)

## 9. Storage: Подключение к БД

**Файл:** `samples/storage/connect_db.go`, [тык](/samples/internal/storage/connect_db.go)

**Что показывает:**
- Подключение к PostgreSQL через `database/sql`
- Настройка пула соединений (MaxOpenConns, MaxIdleConns)
- Использование контекста с таймаутом
- Ping для health-чеков
- Транзакции (`BeginTx`)

**Ключевые моменты:**
- Формат DSN: `postgres://user:password@host:port/dbname?sslmode=mode`
- `SetMaxOpenConns` — контроль максимального числа соединений
- `SetConnMaxLifetime` — пересоздание старых соединений
- `PingContext` — проверка доступности БД с таймаутом

## 10. Storage: Назначение роли

**Файл:** `samples/storage/user_roles.go` (фрагмент), [тык](/samples/internal/storage/user_roles.go)

**Что показывает:**
- Чистый SQL (без ORM)

- `ON CONFLICT DO NOTHING` для защиты от дублирования
- Обработка ошибок через кастомную обёртку `PQError`

**Ключевые моменты:**
- `INSERT ... SELECT` — вставка на основе подзапроса
- `ON CONFLICT DO NOTHING` — игнорирование дубликатов
- `tx.ExecContext` — выполнение с контекстом
- `apperrors.PQError` — трансформация ошибок PostgreSQL в бизнес-ошибки

## 11. Обработка ошибок PostgreSQL

**Файл:** `samples/pkg/errors/pq_errors.go`, [тык](/samples/pkg/estorage.go)

**Что показывает:**
- Трансформация кодов PostgreSQL в бизнес-ошибки
- Обработка контекста (таймауты)
- Классификация ошибок (подключение, целостность, транзакции)
- Добавление контекста операции в ошибку

**Ключевые моменты:**
- `errors.Is(err, context.DeadlineExceeded)` — обработка таймаутов
- `errors.As(err, &pgErr)` — приведение к `pq.Error`
- Полное покрытие кодов ошибок (классы 08, 22, 23, 25, 40, 42, 55, 57)
- Каждому коду — своя бизнес-ошибка

## Что показывает этот код в целом?

1. Чёткое разделение слоёв (handlers → service → storage).
2. Безопасность с помощью JWT, JWKS, bcrypt, HttpOnly cookies.
3. Комментарии к каждому методу.
4. Тестируемость за счёт интерфейсов и внедрения зависимостей.
5. Чистый SQL, обработка ошибок.
