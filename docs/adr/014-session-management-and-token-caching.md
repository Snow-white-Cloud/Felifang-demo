# ADR-014: Архитектура управления сессиями и кэширования токенов

**Дата:** 14.08.2026  
**Статус:** Планируется  
**Автор:** Snow-white-Cloud

## Контекст
В рамках реализации Refresh-токенов, Logout и Rate Limiting требуется определить архитектуру хранения и синхронизации данных между инстансами сервиса.

**Текущие требования:**
1. Хранение Refresh-токенов с возможностью отзыва.
2. Кэширование валидных Access-токенов для снижения нагрузки на CPU и оптимизации по времени.
3. Чёрный список отозванных токенов.
4. Публичные ключи (JWKS) для валидации JWT.
5. Rate Limiting для защищённых эндпоинтов.
6. Поддержка горизонтального масштабирования (несколько инстансов).

## Решение

### 1. Кэш Access-токенов: in-memory с инвалидацией через события
| Характеристика | Решение |
|----------------|---------|
| **Хранилище** | Память инстанса |
| **Время жизни** | Равно TTL Access-токена (15 минут) |
| **Синхронизация** | Redis Pub/Sub для инвалидации при logout |

**Обоснование:**    
Проверка JWT требует криптографических операций (RSA), которые нагружают CPU; in-memory кэш же даёт задержку < 1 мс. При logout/смене пароля все инстансы мгновенно получают событие и очищают кэш для этого пользователя.

### 2. Refresh-токены: Redis
| Характеристика | Решение |
|----------------|---------|
| **Хранилище** | Redis |
| **Время жизни** | 7 дней (конфигурируется) |
| **Операции** | `SET`, `GET`, `DEL`, `DELETE ALL BY USER` |

**Обоснование:**    
Refresh-токены должны быть доступны всем инстансам, что обеспецивает Redis вместе с атомарностью и TTL. При этом сохранена впостота инвалидации (logout, смена пароля).

### 3. Чёрный список (Revocation List): Redis
| Характеристика | Решение |
|----------------|---------|
| **Хранилище** | Redis |
| **Время жизни** | TTL Access-токена |
| **Операции** | `SETEX`, `EXISTS` |

**Обоснование:**    
Централизованное хранение для всех инстансов позволяет просто их синхронизировать. Автоматическое удаление по TTL и мгновенная проверка при каждом запросе.

### 4. Публичные ключи (JWKS): in-memory с автообновлением
| Характеристика | Решение |
|----------------|---------|
| **Хранилище** | Память инстанса |
| **Обновление** | По расписанию (каждые 5 минут) или по событию |
| **Источник** | JWKS-эндпоинт |

**Обоснование:**    
Ключи редко меняются, а доступ к ним требуется часто (почти каждый запрос, если отсутствует в кэше). In-memory даёт минимальную задержку.

### 5. Rate Limiting: Redis + Token Bucket
| Характеристика | Решение |
|----------------|---------|
| **Алгоритм** | Token Bucket |
| **Хранилище** | Redis |
| **Операции** | Lua-скрипты для атомарности |

**Обоснование:**    
Для ограничения кол-ва запросов требуется синхронизация между инстансами. Алгоритм Token Bucket прост в разработке, позволяет обрабатывать кратковременные всплески нагрузки, что полезно для публичных API. Lua-скрипты гарантируют атомарность операций.


## Альтернативы (рассматривались)

### 1. Хранение Access-токенов в Redis
**Плюсы:** централизованное хранение, простота синхронизации.  
**Минусы:** дополнительная сетевая задержка (2-3 мс на запрос), нагрузка на Redis.

**Причина отклонения:** in-memory кэш даёт лучшую производительность, а синхронизация через события решает проблему консистентности.

### 2. Rate Limiting в памяти инстанса
**Плюсы:** простота, отсутствие зависимости от Redis.  
**Минусы:** не работает при нескольких инстансах (лимит можно обойти, переключаясь между инстансами).

**Причина отклонения:** требуется поддержка горизонтального масштабирования.

### 3. Чёрный список в памяти инстанса
**Плюсы:** быстрый доступ.  
**Минусы:** проблемы синхронизации между инстансами.

**Причина отклонения:** при logout на одном инстансе, другие инстансы могут продолжить принимать токен до истечения TTL. Пример: поднятие нового инстанса, у которого чёрный список просто-напросто пуст.

## Ожидаемый эффект
- Повышение производительности за счёт комбинации in-memory кэш и JWKS и минимизирования задержек.
- Поддержка масштабируемости за счёт Redis-хранилища и оаовещений, синхронизирующих состояние между всеми инстансами.
- Поддержка безопасности за счёт мгновенног отзыва токенов через чёрный список и инвалидацию кэша. Это позволяет защититься от 
- Защита от атак с помощью Rate Limiting на основе Redis и алгоритма Token Bucket предотвращает DoS и перебор токенов.
